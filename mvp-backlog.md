# MVP Backlog: языковой ассистент с диалогами и SRS-повторением

**Цель MVP:** дать изучающему язык возможность вести текстовый диалог с LLM, на лету пополнять личную колоду карточек словами из этого диалога и повторять их по интервальному алгоритму (SM-2) — при этом сквозной сценарий должен демонстрировать ключевые микросервисные паттерны (Saga, Outbox, Circuit Breaker, DLQ) для портфолио.

Источник: `mvp-functional-scope.md`. Ничего сверх перечисленных там фич в backlog не добавлено.

## Backlog

| ID | User Story | MoSCoW | Критерии приёмки |
|---|---|---|---|
| US-01 | Как пользователь, я хочу зарегистрироваться и войти по email+паролю, чтобы получить доступ к своему аккаунту | **Must** | JWT выдаётся при логине; повторный email при регистрации отклоняется |
| US-02 | Как пользователь, я хочу указать в профиле родной/изучаемый язык и уровень (A1-C1), чтобы контент подбирался под меня | Should | Поля сохраняются и доступны через `GET /users/{id}/profile`; уровень — enum из 6 значений |
| US-03 | Как пользователь, я хочу видеть свой прогресс (streak, кол-во изученных карточек), чтобы отслеживать динамику обучения | **Must** | Прогресс обновляется автоматически по событию `card.reviewed`, без прямого вызова из Learning Service |
| US-04 | Как пользователь, я хочу видеть список карточек "к повторению сегодня", чтобы знать, что нужно сделать | Should | Список строится consumer'ом события `card.due` |
| US-05 | Как пользователь, я хочу получать in-app уведомление о карточках на повторение, чтобы не забывать заниматься | Should | Уведомление показывается внутри приложения; email/push не реализуются |
| US-06 | Как пользователь, я хочу создавать и просматривать свои колоды карточек, чтобы организовывать словарь по темам | **Must** | CRUD по `/decks` работает; у колоды есть название и источник (manual/conversation) |
| US-07 | Как пользователь, я хочу создавать, просматривать и удалять карточки в колоде (front/back, аудио-ссылка, context_data), чтобы наполнять её вручную | **Must** | CRUD по `/decks/{id}/cards` работает; context_data хранится как произвольный JSON |
| US-08 | Как пользователь, я хочу, чтобы даты следующих повторений считались по алгоритму SM-2, чтобы повторять слова в оптимальные интервалы | **Must** | После `POST /cards/{id}/review` дата следующего показа пересчитывается по формуле SM-2 в зависимости от grade (0–5) |
| US-09 | Как пользователь, я хочу проходить повторение в режиме "помню/не помню", чтобы быстро оценивать карточки | **Must** | Единственный реализованный `ReviewMode` — self-recall; интерфейс допускает добавление других режимов позже |
| US-10 | Как новый пользователь, я хочу автоматически получить стартовую колоду сразу после регистрации, чтобы не начинать с пустого экрана | **Must** | Learning Service создаёт колоду по событию `user.registered` (демонстрация Saga) |
| US-11 | Как пользователь, я хочу, чтобы система раз в день сама собирала мои карточки к повторению, чтобы не считать это вручную | **Must** | Cron-джоб раз в сутки публикует `card.due`, партиционируя по user_id |
| US-12 | Как владелец продукта, я хочу, чтобы событие `card.reviewed` публиковалось надёжно даже при сбое БД/брокера, чтобы прогресс пользователя не терялся | Should | Реализован Transactional Outbox; событие не теряется при падении сервиса между записью в БД и публикацией |
| US-13 | Как пользователь, я хочу, чтобы слово, которое я добавил во время диалога, само превращалось в карточку, чтобы не переносить его вручную | **Must** | Learning Service создаёт карточку по событию `word.enriched` со всеми полученными полями |
| US-14 | Как пользователь, я хочу вести текстовый чат с LLM в реальном времени, чтобы практиковать язык в диалоге | **Must** | Ответ модели стримится через WebSocket `/conversation/{sessionId}` |
| US-15 | Как пользователь, я хочу, чтобы текст диалога был разбит на отдельные слова, чтобы можно было кликнуть по любому из них | **Must** | Простой сплиттер + базовая нормализация; каждое слово кликабельно |
| US-16 | Как пользователь, я хочу кликнуть на незнакомое слово в диалоге и получить его перевод/контекст, чтобы не выходить из чата | **Must** | Клик вызывает `GET /conversation/word/{word}` → результат приходит синхронно или через кэш |
| US-17 | Как пользователь, я хочу, чтобы система помнила последние сообщения текущей сессии диалога, чтобы ответы LLM учитывали контекст | Should | Последние N сообщений сессии хранятся в Redis, не в постоянной БД |
| US-18 | Как пользователь, я хочу (по возможности) говорить и слушать ответы, а не только печатать, чтобы практиковать произношение | Could | Реализуется только если останется время после основного пути; не блокирует остальной скоуп |
| US-19 | Как пользователь, я хочу получать произношение и пример использования слова, чтобы лучше его запомнить | **Must** | Enrichment Service вызывает LLM через абстракцию `LlmProvider` и возвращает произношение + контекст предложения |
| US-20 | Как пользователь, я хочу, чтобы повторный запрос по тому же слову+контексту отвечал мгновенно, чтобы не ждать LLM заново | Should | Результат кэшируется в Redis по ключу `word+context_hash` |
| US-21 | Как владелец продукта, я хочу, чтобы сбои внешнего LLM API не роняли Enrichment Service целиком, чтобы система оставалась отзывчивой | Should | Реализован Circuit Breaker (Resilience4j) на внешние вызовы |
| US-22 | Как владелец продукта, я хочу, чтобы неудавшиеся запросы обогащения не терялись, чтобы их можно было повторить или расследовать | Should | Упавшие обогащения уходят в DLQ с retry-механизмом |
| US-23 | Как пользователь, я хочу обращаться к системе через единую точку входа, чтобы не знать про внутреннюю структуру сервисов | **Must** | API Gateway маршрутизирует запросы ко всем 4 сервисам |
| US-24 | Как пользователь, я хочу, чтобы мои запросы проверялись на валидность токена, чтобы доступ к данным был защищён | **Must** | Gateway валидирует JWT, выпущенный User Service, перед проксированием запроса |
| US-25 | Как владелец продукта, я хочу ограничивать частоту запросов с одного IP, чтобы защитить систему от перегрузки | Should | Базовый per-IP rate-limiting на Gateway |

**Итог по приоритетам:** Must — 15 из 25 (60%), Should — 9 (36%), Could — 1 (4%), Won't — вынесено в отдельный раздел ниже.

## Out of scope (Won't) — зафиксировано, чтобы скоуп не расползался

**User Service**
- OAuth/соцвход — экономия времени, не даёт архитектурной ценности для демо
- Реальная доставка email/push — интеграция с внешним провайдером не демонстрирует новый паттерн
- GDPR-экспорт данных, настройки приватности, локализация UI профиля, роли/права (admin) — не нужны для сквозного демо-сценария

**Learning Service**
- Экспорт колод (Anki/CSV/PDF) — полезно пользователю, но не для демонстрации; future work
- Режимы карточек "написание" и "аудио" — оставлен только архитектурный контракт (`ReviewMode`), реализации нет
- Публичные/шаренные колоды между пользователями — вырезано
- Content Ingestion Bus (плагин-система загрузки контента) — полностью вырезано из MVP
- Настраиваемые параметры SRS / выбор алгоритма (кроме SM-2) — вырезано

**Conversation Service**
- Голосовой ввод/вывод как обязательная часть MVP — STT/TTS остаётся только необязательным stretch-сценарием (US-18)
- Отдельный tool-use фреймворк ("скилы" для контекста/колоды/словаря/ошибок) — сведено к одному сценарию lookup+add-to-deck
- Анализ ошибок пользователя (mistake mining) — не реализуется; топик `conversation.error` может остаться в схеме на будущее
- Мультисессионность / история диалогов за всё время — вырезано

**Enrichment Service**
- Собственный/файнтюненный ASR/TTS — только обёртка над внешним API, и то как stretch goal
- Видео-контекст к слову (timecode) — полностью вырезано, context_data только текстовый
- Мультипровайдерность с авто-fallback между LLM-вендорами — архитектурный задел (интерфейс), второй провайдер не реализуется

**API Gateway**
- API-версионирование и сложная трансформация запросов — не нужны для демонстрации

## Вопросы / требует уточнения

- Какие именно значения принимает grade в `POST /cards/{id}/review` (0–5) и как они соотносятся с формулой SM-2 — в файле не детализировано.
- В чём именно выражается "in-app уведомление" (US-05): пуш внутри UI в реальном времени или просто бейдж/счётчик при следующем заходе — не указано.
- Какой лимит rate-limiting на Gateway (запросов/сек на IP) — в файле не задан, выбор значения не зафиксирован.
- Формат "истории диалога" в Redis (US-17): сколько сообщений N хранится и TTL сессии — не указано явно.
