# Функциональная спецификация MVP (микросервисный вариант)
### Что именно входит в каждый сервис — детальный скоуп

Документ дополняет `mvp-microservices-roadmap.md`. Здесь — конкретный список фич по каждому сервису: что делаем, что сознательно выкидываем, и какие эндпоинты/события это даёт.

Принцип отбора: фича остаётся в MVP, если она либо (а) нужна для сквозного демо-сценария, либо (б) даёт повод продемонстрировать конкретный паттерн (Saga, Outbox, Circuit Breaker и т.д.). Всё остальное — вырезано без сожаления.

---

## 1. User Service

### Входит

| Фича | Комментарий |
|---|---|
| Регистрация / логин (email+пароль) | JWT, без соцсетей и OAuth — экономия времени |
| Профиль: native_lang, target_lang, уровень (A1-C1, просто enum) | Минимум полей |
| Хранение прогресса (streak, всего изученных карточек) | Обновляется через событие `card.reviewed`, не напрямую |
| Список due-notifications (что показать пользователю "сегодня N карточек к повторению") | Consumer события `card.due` |
| Простейшие уведомления — **только in-app**, без email/push | push/email — интеграция с внешним провайдером, не даёт нового архитектурного опыта |

### Не входит (вырезано)

- OAuth/социальный вход
- Email/push-уведомления (реальная доставка)
- Настройки приватности, GDPR-экспорт данных
- Мультиязычный UI/локализация профиля
- Роли/права (admin-панель) — если не нужно для демо

### API / события

```
REST:
POST /users/register
POST /users/login
GET  /users/{id}/profile
GET  /users/{id}/progress

Kafka:
produces: user.registered
consumes: card.reviewed  -> обновить progress
consumes: card.due       -> обновить due-notifications список
```

## 2. Learning Service (ядро)

### Входит

| Фича | Комментарий |
|---|---|
| CRUD колод (deck) | Название, источник (manual/conversation) |
| CRUD карточек (card): front/back текст, аудио-ссылка, context_data (JSON) | context_data — просто поле, без отдельного видео-пайплайна |
| **SRS-алгоритм — только SM-2** | FSRS — сложнее, не даёт нового опыта для стажировки, SM-2 отлично демонстрирует сам факт наличия алгоритма |
| Один режим повторения: **самостоятельная оценка (self-recall, "помню/не помню")** | Остальные 2 режима (написание, аудио) — вырезаны из MVP, оставлены как задел (интерфейс `ReviewMode`, но 1 реализация) |
| Автосоздание стартовой колоды при регистрации (демонстрация Saga) | Consumer `user.registered` |
| Cron-джоб: раз в день собрать due-cards и опубликовать `card.due` | Ядро демонстрации батчинга + партиционирования по user_id |
| Transactional Outbox для `card.reviewed` | Ключевой пункт резюме |

### Не входит (вырезано)

- Экспорт в Anki/CSV/PDF и т.д. — фича полезная для пользователя, но не для собеседования; выносим как "future work"
- Режимы "написание" и "аудио" — оставляем архитектурный контракт (interface), но не реализуем сами режимы
- Публичные/шаренные колоды между пользователями
- Плагин-система загрузки контента (Content Ingestion Bus) — из исходных требований, полностью вырезана из MVP
- Настройка параметров SRS-алгоритма пользователем (advanced settings)

### API / события

```
REST:
POST   /decks
GET    /decks/{userId}
POST   /decks/{id}/cards
GET    /decks/{id}/cards/due
POST   /cards/{id}/review   {grade: 0-5}

Kafka:
produces: card.reviewed, card.due
consumes: user.registered  -> создать дефолтную колоду
consumes: word.enriched    -> добавить карточку из диалога (со всеми полями от Enrichment)
```

## 3. Conversation Service

### Входит

| Фича | Комментарий |
|---|---|
| **Только текстовый чат с LLM** (без голоса в MVP-ядре) | Голос — Фаза 3, если останется время; текстовый чат уже даёт WebSocket-стриминг для демонстрации |
| Токенизация текста по словам (простой сплиттер + базовая нормализация) | Не NLP-грейд, достаточно для клика по слову |
| Клик по слову → запрос обогащения (sync к Enrichment или через кэш) | |
| История диалога (последние N сообщений сессии) в Redis | Не персистентная БД — не нужно для MVP |
| STT/TTS — **опционально, если есть время после основного пути** | Явно помечено как "stretch goal", не блокирует основной скоуп |

### Не входит (вырезано)

- Голосовой ввод/вывод как обязательная часть MVP (перенесено в stretch goal)
- "Скилы для улучшения данных" (контекст, колода, словарь, ошибки как отдельные LLM-инструменты/functions) — сведено к одному сквозному сценарию lookup слова, без полноценного tool-use фреймворка
- Анализ ошибок пользователя в диалоге (mistake mining) как отдельная фича — не реализуется в MVP, хотя топик `conversation.error` можно оставить в схеме на будущее
- Мультисессионность / история диалогов за все время

### API / события

```
REST/WS:
WS   /conversation/{sessionId}          - стриминг сообщений LLM
GET  /conversation/word/{word}?context= - sync-запрос обогащения (проксирует в Enrichment)

Kafka:
produces: word.looked-up
consumes: word.enriched  -> прокинуть во фронт через WS, если сессия ещё активна
```

## 4. Enrichment Service

### Входит

| Фича | Комментарий |
|---|---|
| Единая точка вызова LLM API (произношение, контекст предложения) | Абстракция `LlmProvider` за интерфейсом |
| Кэш результатов обогащения (Redis, ключ word+context_hash) | |
| Circuit Breaker на внешние вызовы (Resilience4j) | Ключевой пункт резюме |
| DLQ + retry для упавших обогащений | |

### Не входит (вырезано)

- Собственный/файнтюненный ASR/TTS — только обёртка над внешним API, и то как stretch goal
- Видео-контекст (timecode из видео-источника) — полностью вырезано, `context_data` заполняется только текстовым контекстом предложения
- Мультипровайдерность с автоматическим fallback между разными LLM-вендорами — оставляем как архитектурный задел (интерфейс), но не реализуем 2-й провайдер в MVP

### API / события

```
REST (для sync-запросов от Conversation):
GET /enrich/word/{word}?context=

Kafka:
consumes: word.looked-up
produces: word.enriched, enrichment.failed (DLQ)
```

## 5. API Gateway

Чистая инфраструктура, не бизнес-функционал:
- Роутинг к 4 сервисам
- JWT-валидация (простая, делегирует User Service выпуск токена)
- Rate-limiting (базовый, per-IP)
- Без API-версионирования, без сложной трансформации запросов — не нужно для демонстрации

## Итоговая сквозная демо-сценария (то, что должно работать end-to-end к неделе 11)

1. Пользователь регистрируется → **User Service** публикует `user.registered` → **Learning Service** автоматически создаёт стартовую колоду (Saga).
2. Пользователь открывает текстовый чат → **Conversation Service** стримит ответ LLM.
3. Пользователь кликает на незнакомое слово → **Conversation Service** запрашивает обогащение → **Enrichment Service** (кэш/LLM) → возвращает произношение + контекст.
4. Пользователь жмёт "добавить в колоду" → событие `word.looked-up` → **Enrichment** обогащает и публикует `word.enriched` → **Learning Service** создаёт карточку.
5. На следующий день cron в **Learning Service** собирает due-cards, публикует `card.due` → **User Service** обновляет список уведомлений.
6. Пользователь проходит сессию повторения (self-recall режим) → **Learning Service** через Outbox публикует `card.reviewed` → **User Service** обновляет streak/progress.

Это один непрерывный путь, который использует все 6 топиков Kafka, обе Saga-точки, Outbox, Circuit Breaker и DLQ — то есть весь список "что забрать в резюме" из предыдущего документа подтверждается реальным работающим кодом, а не отдельными несвязанными демками.

## Полный список того, что вырезано из исходных требований (свод)

| Исходная фича | Статус в MVP |
|---|---|
| Распознавание речи (STT) | Stretch goal, не в основном скоупе |
| Синтез речи (TTS) | Stretch goal |
| LLM-скилы (контекст/колода/словарь/ошибки как отдельные tools) | Сведено к одному сценарию lookup+add-to-deck |
| Анализ ошибок в диалоге | Вырезано |
| Видео-контекст к слову | Вырезано |
| Режимы карточек: написание, аудио | Архитектурный контракт есть, реализации нет |
| Экспорт колод в разные форматы | Вырезано |
| Гибкая plugin-система загрузки контента | Полностью вырезано |
| Настраиваемый алгоритм SRS (несколько на выбор) | Только SM-2 |
| Соц. вход / роли / приватность | Вырезано |
